# Contributing to Collection

Thank you for contributing to **Collection**, an open-source library of industry- and enterprise-oriented documents and materials maintained by **YankiDev** ([yankidev.com](https://yankidev.com)).

By contributing, you agree that your contributions are licensed under the [MIT License](LICENSE) and that original material you submit may be published under Copyright © YankiDev (yankidev.com) as part of this project, with attribution to contributors in git history and release notes where appropriate.

## Ways to contribute

- Fix typos, broken links, or outdated facts
- Improve clarity for enterprise / production use cases
- Add new guides for frameworks, tools, architecture, or standards
- Submit templates, checklists, or learning paths
- Propose structural improvements via issues

## Before you start

1. Search existing issues and pull requests to avoid duplicates.
2. For large new topics, open an issue first to align on scope.
3. Keep content practical, accurate, and vendor-neutral where possible.

## Document guidelines

- Place content under the correct `docs/` category.
- Use clear headings and short paragraphs.
- Include a metadata table (status, audience, level, last reviewed).
- Call out **when not to use** a pattern or tool.
- Prefer primary sources and official docs for version-sensitive facts.
- Do not copy proprietary vendor training or copyrighted material verbatim.
- Do not include secrets, credentials, customer data, or internal-only URLs.

### Suggested file naming

```text
docs/<category>/<topic-kebab-case>.md
```

Examples:

- `docs/frameworks/spring-boot-enterprise-basics.md`
- `docs/tools/github-actions-ci-checklist.md`
- `docs/templates/architecture-decision-record.md`

## Pull request process

1. Fork the repository (or create a branch if you have write access).
2. Create a focused branch: `docs/short-description` or `fix/short-description`.
3. Make your changes and preview Markdown locally.
4. Update related index/README files if you add a new document.
5. Open a pull request with:
   - What changed and why
   - Category and audience
   - Any sources you relied on for version-specific claims
6. Respond to review feedback promptly.

## Style

- Use American English spelling consistently unless quoting external standards.
- Prefer concrete examples over abstract jargon.
- Use tables for comparisons and checklists for procedures.
- Avoid promotional language and unverifiable claims.
